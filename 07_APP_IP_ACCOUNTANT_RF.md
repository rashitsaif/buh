# 07_APP_IP_ACCOUNTANT_RF.md

## Назначение файла

Этот файл — проектная инструкция для ИИ-агента, который разрабатывает веб-приложение «AI-бухгалтер для ИП в РФ».

Цель приложения — максимально автоматизировать типовой бухгалтерский, налоговый и документный учет индивидуального предпринимателя в России: учет доходов и расходов, контроль налоговых режимов, расчет налогов и взносов, календарь обязательств, подготовка документов, напоминания и объяснение действий простым языком.

Приложение должно строиться как надежный финансово-юридический продукт. Нельзя делать «красивый калькулятор» без проверки правил, версии налоговых норм, логов, ручного подтверждения пользователем и понятных ограничений.

---

## Главный принцип продукта

Приложение должно работать как операционный помощник, который закрывает большую часть рутинных задач бухгалтера для типового ИП, но не должно скрывать от пользователя юридически значимые действия.

Критические действия должны требовать подтверждения пользователя:

- отправка отчетности;
- формирование платежных документов;
- подтверждение налогового расчета;
- загрузка данных из банка;
- изменение налогового режима;
- удаление операций;
- изменение правил расчета;
- массовые исправления учета.

Приложение не должно обещать абсолютную юридическую замену бухгалтера без оговорок. Корректная формулировка продукта:

> Веб-приложение автоматизирует учет, расчеты, документы и налоговый календарь для ИП в РФ, снижая потребность в ручной бухгалтерии. Пользователь подтверждает юридически значимые действия самостоятельно.

## Целевая аудитория

Основные пользователи:

1. ИП без сотрудников.
2. ИП на УСН «Доходы».
3. ИП на УСН «Доходы минус расходы».
4. ИП на ПСН.
5. ИП на НПД / самозанятость, если сценарий поддерживается.
6. Небольшие ИП с 1–5 сотрудниками — не в MVP, только позже.

Приоритет MVP: ИП без сотрудников на УСН «Доходы» и УСН «Доходы минус расходы».

## Бизнес-цель MVP

Создать первую стабильную версию, которая позволяет ИП:

1. Завести профиль предпринимателя.
2. Выбрать налоговый режим.
3. Вносить или импортировать доходы и расходы.
4. Видеть текущие налоговые обязательства.
5. Получать календарь платежей и отчетности.
6. Получать понятные подсказки, что и когда платить.
7. Формировать черновики документов и отчетов.
8. Хранить историю операций и расчетов.

MVP не должен начинаться с прямой интеграции с ФНС, банками, ЭДО, кассами и сложной отправкой отчетности. Сначала — надежный учет, расчеты, календарь и экспорт.

## Важные налоговые правила: как хранить и использовать

Все ставки, сроки, лимиты, пороги и формулы должны храниться как версионированные налоговые правила.

Запрещено жестко зашивать налоговые параметры только в код без версии и даты действия.

Нужно создать сущность tax_rule_versions или аналогичную структуру.

Каждое правило должно иметь:

- код правила;
- налоговый режим;
- регион, если применимо;
- год;
- дату начала действия;
- дату окончания действия;
- значение;
- источник;
- комментарий;
- дату последней проверки;
- статус: draft / active / archived.

Пример правил:

- USN_INCOME_RATE;
- USN_INCOME_EXPENSE_RATE;
- INSURANCE_FIXED_AMOUNT;
- INSURANCE_EXTRA_PERCENT;
- INSURANCE_EXTRA_THRESHOLD;
- INSURANCE_EXTRA_CAP;
- USN_DECLARATION_DEADLINE_IP;
- USN_ADVANCE_PAYMENT_DEADLINE_Q1;
- USN_ADVANCE_PAYMENT_DEADLINE_Q2;
- USN_ADVANCE_PAYMENT_DEADLINE_Q3;
- PSN_APPLICATION_DAYS_BEFORE_START;
- NPD_RATE_INDIVIDUALS;
- NPD_RATE_COMPANIES.

Перед реализацией расчетов агент обязан заложить возможность обновления правил без переписывания бизнес-логики.

## Источники правды

Для налоговых и юридически значимых данных использовать только официальные источники или данные, явно загруженные владельцем проекта.

Приоритет источников:

1. ФНС России.
2. Налоговый кодекс РФ.
3. Госуслуги / официальные государственные сервисы.
4. СФР — для задач с сотрудниками.
5. Официальные документы платежных систем, банков, операторов ЭДО, онлайн-касс.

Запрещено строить налоговую логику только по блогам, статьям, форумам и пересказам.

Если правило устарело или не подтверждено официальным источником, оно не должно автоматически применяться как активное.

## Обязательное предупреждение внутри приложения

В интерфейсе приложения должна быть понятная формулировка:

> Расчеты формируются на основе введенных данных и актуальных правил, настроенных в системе. Перед оплатой налогов, отправкой отчетности или юридически значимыми действиями проверьте данные и подтвердите действие.

Предупреждение не должно пугать пользователя, но должно защищать продукт от ложного обещания полной юридической безошибочности.

## Tax Engine

Нужен отдельный модуль tax engine.

Он должен:

1. Принимать профиль ИП.
2. Принимать период.
3. Принимать подтвержденные операции.
4. Загружать активные tax_rule_versions.
5. Выполнять расчет.
6. Возвращать подробную расшифровку.
7. Сохранять snapshot входных данных.
8. Сохранять snapshot примененных правил.
9. Позволять пересчитать период при изменении данных.
10. Не затирать старые подтвержденные расчеты без истории.

Результат должен быть объяснимым:

- доходы за период;
- расходы за период;
- налоговая база;
- ставка;
- сумма налога;
- страховые взносы;
- уменьшение налога, если применимо;
- итог к оплате;
- срок оплаты;
- предупреждения.

## AI-помощник

AI-помощник не должен быть источником истины для налоговых расчетов.

AI-помощник может:

- объяснять расчет простым языком;
- помогать классифицировать операции;
- подсказывать, какие документы нужны;
- объяснять налоговый календарь;
- помогать составлять счета, акты, письма;
- объяснять ошибки импорта;
- помогать подготовить вопрос в поддержку.

AI-помощнику запрещено:

- самостоятельно подтверждать налоговые расчеты;
- самостоятельно отправлять отчетность;
- самостоятельно оплачивать налоги;
- менять налоговые правила;
- принимать юридически значимые решения без подтверждения пользователя.

Все AI API вызываются только через backend.

## Импорт банковских операций

MVP должен поддерживать CSV/XLSX импорт.

Правила:

1. Пользователь загружает файл.
2. Backend парсит файл.
3. Система показывает предпросмотр.
4. Пользователь подтверждает импорт.
5. Дубли определяются по дате, сумме, описанию, счету и внешнему id, если есть.
6. Спорные строки получают статус needs_review.
7. Все действия логируются.

Нельзя автоматически записывать импортированные операции как подтвержденные без предпросмотра, если формат файла не распознан надежно.

## Безопасность и доступы

Обязательные правила:

1. Пользователь видит только свои данные.
2. Все таблицы с пользовательскими данными защищены RLS или аналогичным механизмом.
3. Секретные ключи не попадают во frontend.
4. AI API только через backend.
5. Импорт файлов проверяется на формат и размер.
6. Все критические действия пишутся в audit_logs.
7. Удаление финансовых операций должно быть мягким или с аудитом.
8. Админские действия требуют отдельной роли.
9. Нельзя редактировать tax_rule_versions без лога.
10. Нельзя менять подтвержденный расчет без создания новой версии.

## UX-принципы

Интерфейс должен быть простым для ИП без бухгалтерского опыта.

Писать не бухгалтерским языком, а понятными действиями:

- «Добавить доход»;
- «Добавить расход»;
- «Проверить налог»;
- «Что оплатить в этом месяце»;
- «Сформировать счет»;
- «Импортировать выписку»;
- «Проверить ошибки».

Каждый расчет должен объясняться:

- откуда взялась сумма;
- какие операции вошли;
- какие правила применены;
- что нужно сделать дальше.

## Критерии готовности MVP

MVP можно считать готовым, если:

1. Пользователь регистрируется и входит.
2. Пользователь создает профиль ИП.
3. Пользователь добавляет доходы и расходы.
4. Пользователь импортирует банковскую выписку.
5. Пользователь видит расчет налога за период.
6. Пользователь видит страховые взносы.
7. Пользователь видит календарь обязательств.
8. Пользователь формирует документы и экспорт.
9. Пользователь получает понятное объяснение расчетов.
10. Все критические действия логируются.
11. Пользователь не видит чужие данные.
12. Секретные ключи не попадают во frontend.
13. Сборка проходит.
14. Основные сценарии проверены.

## Обязательная позиция агента

Агент должен постоянно помнить:

Это приложение работает с налогами, деньгами, персональными данными и юридически значимыми действиями.

Поэтому запрещено:

- делать непроверенные расчеты как финальные;
- скрывать ограничения;
- использовать устаревшие правила без статуса;
- подменять backend-логику frontend-калькулятором;
- обещать пользователю безошибочную замену бухгалтера;
- автоматически выполнять юридически значимые действия без подтверждения.

Надежность важнее скорости.
